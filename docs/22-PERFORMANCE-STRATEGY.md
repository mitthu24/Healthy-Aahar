# 22 — Performance Strategy

## 1. Budgets

Budgets, not aspirations: exceeding them fails CI.

| Surface | LCP p75 | INP p75 | CLS | First-load JS |
|---|---|---|---|---|
| Marketing home | ≤ 1.8s | ≤ 200ms | ≤ 0.05 | ≤ 100KB gz |
| Marketing product | ≤ 1.8s | ≤ 200ms | ≤ 0.05 | ≤ 110KB gz |
| Customer home | ≤ 2.0s | ≤ 200ms | ≤ 0.10 | ≤ 160KB gz |
| Customer product | ≤ 2.0s | ≤ 200ms | ≤ 0.10 | ≤ 170KB gz |
| Customer checkout | ≤ 2.2s | ≤ 200ms | ≤ 0.10 | ≤ 190KB gz |
| Admin (any) | ≤ 3.0s | ≤ 300ms | ≤ 0.10 | ≤ 350KB gz |

Test conditions: Moto G Power class device, 4G (1.6 Mbps, 150ms RTT), cold cache.
Admin budgets are looser deliberately — it is a desktop tool on good connectivity, and
spending effort there instead of on the storefront would be misallocated.

| API | Target |
|---|---|
| Public catalogue reads | p95 ≤ 150ms |
| Authenticated reads | p95 ≤ 300ms |
| Cart mutations | p95 ≤ 250ms |
| Order placement | p95 ≤ 600ms |
| Slot availability | p95 ≤ 200ms |

## 2. The four journeys that must be fast

1. **First paint of the marketing home** — acquisition depends on it.
2. **Category → product browsing** — must feel instant, or people stop browsing.
3. **Add to cart** — optimistic, ≤ 100ms perceived.
4. **Checkout to order placed** — ≤ 2s end to end; this is where revenue is lost.

Everything below serves these four.

## 3. Rendering strategy

| Surface | Strategy | Why |
|---|---|---|
| Marketing static pages | SSG | Never changes between deploys |
| Marketing catalogue | ISR 300s + on-demand revalidation | Fresh prices without per-request cost |
| Customer home | RSC with streaming | Shell is instant; rails stream in |
| Customer listing | RSC + client pagination | First page server-rendered, subsequent pages fetched |
| Customer product | RSC, client islands for variant and cart | Minimal JS on the highest-traffic page |
| Cart, checkout | Client components | Highly interactive, always live data |
| Admin | Client-rendered SPA-style | Behind auth, no SEO, heavy interactivity |

**Streaming:** the customer home sends the header, search and category rail immediately, then
streams product rails as their queries resolve. A slow bestsellers query delays one rail, not
the page.

## 4. Images

Images are the dominant byte cost for a food business.

- Originals in R2 at 1200×1200; Cloudflare generates 400/800/1200 variants in AVIF with WebP
  and JPEG fallbacks.
- `next/image` with explicit `width`/`height` and `sizes` — no layout shift, no oversized
  downloads on mobile.
- Above-the-fold hero: `priority` + `<link rel="preload">`. Everything else lazy-loads with
  `loading="lazy"` and a 200px root margin.
- LQIP blur placeholders (`product_images.blur_data_url`) generated by the upload worker.
- `Cache-Control: public, max-age=31536000, immutable` on CDN variants — the URL contains a
  content hash, so cache invalidation is a new URL.

Target: product card image ≤ 25KB at 400px AVIF; hero ≤ 80KB.

## 5. Caching

| Layer | Content | TTL | Invalidation |
|---|---|---|---|
| Cloudflare edge | Marketing HTML | 300s | Purge by tag on publish |
| Cloudflare edge | Images, hashed assets | 1 year | Immutable URLs |
| Next.js ISR | Marketing catalogue pages | 300s | On-demand revalidate webhook |
| API `Cache-Control` | Public catalogue | `s-maxage=60, swr=300` | ETag |
| API in-process | Settings, zones, slots, categories | 60s | Version counter on write |
| TanStack Query | Catalogue, cart, orders | stale-while-revalidate | Mutation invalidation |
| Browser | Static assets | 1 year | Content hash |

Authenticated responses are **never** edge-cached and carry
`Cache-Control: private, no-store`. Cart, orders and subscriptions must not be shared between
users under any circumstances, and the rule is asserted by an integration test that fails if
an authenticated route omits it.

## 6. Database performance

- Every query on a hot path uses an index from the list in doc 04 §13; `EXPLAIN` output is
  reviewed for any new query on the checkout or catalogue path.
- **No `N+1`.** Prisma `include` or explicit batch loading; a lint rule flags queries inside
  loops.
- **No unbounded queries.** Every list endpoint is cursor-paginated with a maximum limit.
- **Cursor, not offset** — constant time regardless of depth, and stable under concurrent
  writes.
- **Connection pooling** in the always-on API process (pool size tuned to Railway Postgres
  limits) — one of the main reasons the API is not serverless (doc 02 §3).
- **Denormalised counters** (`customer_profiles.total_orders`, `slot_capacity.booked_count`,
  `products.popularity_score`) maintained transactionally, so dashboards never aggregate
  across `orders`.
- **Nightly rollups** (P2) for reporting, so analytics never competes with checkout.
- `pg_stat_statements` reviewed weekly; any query above 100ms p95 gets an issue.

## 7. Bundle discipline

- Server components by default; `'use client'` only where interactivity requires it.
- Route-level code splitting, plus dynamic imports for heavy, rarely-used components
  (charts, date pickers, rich editors).
- `@next/bundle-analyzer` in CI with a hard size gate per app.
- Tree-shakeable icon imports (`lucide-react/icons/*`, never the barrel).
- No moment.js, no lodash barrel; `date-fns` with per-function imports.
- Self-hosted variable fonts, subset to Latin, `font-display: swap`, preloaded.
- No third-party script above the fold; analytics loads with `strategy="lazyOnload"`.

## 8. Perceived performance

Measured speed and felt speed are different problems.

- **Skeletons that match the final layout**, never spinners for content.
- **Optimistic cart updates** — the count changes instantly and rolls back on failure.
- **Prefetch on intent** — `next/link` prefetches on viewport entry; product cards prefetch
  their detail route on hover or touchstart.
- **Instant navigation** for cached routes via the App Router cache.
- **Stale-while-revalidate** — show cached catalogue immediately, refresh in the background.
- **No layout shift** — reserved space for every image, badge and price.

## 10. Monitoring and gates

| Tool | Gate |
|---|---|
| Lighthouse CI | Runs on every PR against a preview deployment; fails below the budget |
| `@next/bundle-analyzer` | Fails on a size regression above the per-app cap |
| Vercel Analytics | Real-user CWV p75 by route; weekly review |
| Sentry performance | API transaction traces, slow-endpoint alerting |
| `pg_stat_statements` | Weekly slow-query review |
| k6 load test | Before launch and before any expected peak |

**Load test targets (pre-launch):** 100 concurrent users browsing, 20 concurrent checkouts
against the same slot, and a subscription-materialisation run over 1,000 subscriptions — all
with p95 within budget and **zero over-booking**, which is simultaneously a performance test
and a correctness test of the `slot_capacity` locking (doc 24 §7).

## 11. Anti-patterns to reject in review

| Anti-pattern | Why it is rejected |
|---|---|
| `SELECT *` on a hot path | Fetches `cost_paise` and other fields we must not serialise, and inflates payloads |
| Offset pagination | Degrades with depth; unstable under concurrent writes |
| Aggregating `orders` for a dashboard widget | Use denormalised counters or a rollup |
| Client-side filtering of a full catalogue | Ships the whole dataset to the device |
| A spinner covering the whole page | Destroys perceived performance |
| Images without dimensions | Guaranteed CLS |
| Fetching in a `useEffect` waterfall | Serialises what should be parallel |
| Barrel imports from large libraries | Defeats tree-shaking |
